# FactoryTraj-Bench Data Contract v0.1

## Decision

FactoryTraj-Bench represents one industrial reasoning item as:

```text
production context
+ synchronized observation window
+ candidate actions
+ SOP evidence
+ question
-> structured state, event, cause, action and outcome targets
```

The contract is benchmark-first. It does not assume Cosmos 3 is the winning
backbone, and it does not authorize any model output to control a production
PLC.

## Separation between input and ground truth

Every item has two hard boundaries:

- `model_input`: the only payload a model may receive;
- `ground_truth`: labels used by training/evaluation code after the prediction.

Code must call `jwm.factorytraj.model_input_view`. Passing the complete item to
a model is a protocol violation. The validator recursively rejects target-like
keys such as `answer`, `root_cause`, `fault_label`, `target` and
`ground_truth` from model-facing payloads.

`causal_level`, `template_id` and `template_type` are evaluation metadata and
are also removed by `model_input_view`. This prevents a model from exploiting
the template prior measured by the context-blind baseline.

## Item identity and provenance

`item_id` uniquely identifies the benchmark item. `source.source_episodes`
preserves every referenced source trajectory, including both trajectories in a
comparative sample. `split.split_group` is derived from those source episodes.
The same split group must never cross train, validation or test.

Random row splits and overlapping-window splits are prohibited.

## Model input

### Production context

The context includes cell, machine, asset type, product/work order, operating
mode, target rate and extensible metadata. Missing source context is represented
as `null`; it must not be guessed from the answer.

### Observation window

The target operational window is the previous 60 seconds. Each stream contains:

- timestamps and their source-native unit;
- `sensor_history`;
- `control_signals`;
- time-varying `machine_context`;
- optional video, image, audio, spectrogram or plot references;
- data-quality metadata.

Each numerical block stores channel metadata, a `[time, channel]` value matrix
and a matching validity mask. Missing values remain missing and are never
silently zero-filled.

`stream_relationship` distinguishes single, paired, multiple and option-only
items. Paired FactoryBench records must preserve both series.

### Candidate actions and SOP

Candidate actions are typed, bounded proposals with target, parameters,
preconditions and authorization. SOP content is represented as addressable
document/step records. The model ranks or describes actions; deterministic
safety and authorization remain external.

## Task and target

`task.benchmark_tasks` maps an item to FactoryTraj capabilities B0–B10.
`causal_level` preserves FactoryBench L1–L4 for stratified reporting.

Ground truth can hold:

- latent/belief state;
- events and timing;
- root causes;
- selected action;
- immediate/delayed outcome;
- the task-specific response;
- evidence pointers;
- label confidence and provenance.

The FactoryBench examples only populate labels present in the source. Empty
state/action/outcome fields mean “not supplied”, not a negative label.

## Model output

`factorytraj_output.schema.json` requires:

- belief state with probability;
- evidence pointers;
- next events and probabilities;
- ranked root causes;
- ranked actions;
- expected outcomes;
- task response;
- calibrated confidence;
- explicit abstention and reason.

The output exposes evidence, not private chain-of-thought.

## Governance

Every item records permitted use, commercial-training permission,
redistribution status and personal-data status. FactoryBench examples are:

- `research_only`;
- not admitted for commercial training;
- derived from CC BY-NC 4.0 material.

This restriction must propagate to every derivative manifest.

## FactoryBench mapping

The ten examples in `factorybench_samples_v0.1.json` cover:

- L1 prediction and comparison;
- L2 anomaly detection and comparison;
- L3 prediction, intervention outcome and trajectory outcome;
- L4 troubleshooting and optimization;
- both single-stream and paired-stream evidence.

They are compact head/tail samples generated by the earlier audit. They are
appropriate for schema and visualization tests only. Benchmark scores must use
the complete source records.

FactoryBench provides sensor and control channels but does not consistently
provide static production context, SOP, executed action or measured delayed
outcome. Those gaps remain explicit `null`, empty list or empty object fields.

## Validation and admission

Run:

```bash
python scripts/build_factorytraj_samples.py
python scripts/validate_factorytraj_contract.py
python -m pytest tests/test_factorytraj_contract.py -q
```

Admission requires:

1. both JSON Schemas are valid Draft 2020-12 schemas;
2. every example passes the item schema;
3. all four causal levels are represented;
4. single and paired streams are represented;
5. no target-like field reaches `model_input_view`;
6. stream matrices and validity masks match timestamps/channels;
7. source split groups do not leak;
8. source license restrictions are enforced.

## Known v0.1 limitations

- FactoryBench timestamps and units are source-specific and incompletely
  documented in compact examples.
- Machine context and SOP require provenance-safe joins for some sources.
- The example pack is not a replacement for a locked real-machine test set.
- B2, B7 and B10 require additional datasets or annotations.
- Action-conditioned world-model claims require measured action–outcome
  trajectories, which FactoryBench only partially supplies.
